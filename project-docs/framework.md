### 0.2 两个容易做错的地方

1. **首页底图的图片填充 opacity 是 `0.10`，不是满不透明。**
   这个值只存在于 Figma 的 `fills[0].opacity` 里，看渲染图完全猜不出来。
   按满不透明铺会把正文压得读不清 —— 第一版就踩了，实测约 0.66 强度，正文不可读。
   实现方式：`#s0::before` 独立图层铺图 + `opacity:.10`，内容 `z-index:1`。

2. **五档圆点尺寸递变，但圆心必须对齐。**
   设计稿尺寸依次为 `30 / 24 / 16 / 24 / 30`px，圆心全部落在距卡片左边 **31px**，文字统一在 **60px**。
   直接给不同尺寸的圆点相同 margin 会让圆心错开，看起来参差。
   做法：卡片 `padding:0 16px`，再给每档单独配 `margin-left / margin-right` 把圆心拉回同一条竖线。

## 〇之二、资产规格（最终版）

### A. 插图

21 张水彩插图由用户提供，统一 1086×1448（3:4），**画面下方已烘焙乐器中文名与产地**。
这解释了 Figma 设计稿里为什么结果页那块图片区域含文字 —— 因此：

> **结果页不要再用 HTML 输出乐器中文名**，否则同一个名字会出现两次。
> 英文名与科属用一行小字补充（插图里没有这两项）。

压缩成两套尺寸（`docs/_build_images.py`）：

| 用途 | 文件 | 尺寸 | 平均体积 |
|---|---|---|---|
| 结果页海报 | `img/<id>.jpg` | 600×800 (3:4) | 24 KB |
| 图鉴缩略图 | `img/<id>_t.jpg` | 240×240 方裁 | 4.5 KB |

缩略图**必须方裁画面上部**：3:4 海报缩到 ~100px 宽时，底部烘焙的乐器名完全不可读，
留着只是一片噪点；裁掉文字只留器物，再由 HTML 文字提供可读名字。

原图 25 MB → 两套共 0.57 MB（**减少 98%**）。

> 踩过的坑：给 `<img>` 加了 `width`/`height` 属性防布局抖动，但属性会生成**确定的
> used height**，压过 CSS 的 `aspect-ratio`，缩略图被拉成 103×240 的竖条。
> 必须同时写 `height:auto`。

### B. 音频

20/21 件有 10 秒片段。**统一响度是必须的**：原始素材来自不同录音者，
实测 RMS 跨度达 **36.3 dB**（恰朗戈 −49.5 dB 几乎听不见，杜杜克管 −13.2 dB 很响），
手机上切换乐器会被忽大忽小的音量吓到。归一化后压到 **3.7 dB**。

处理参数（`docs/_normalize_audio.py`）：目标 RMS −20 dBFS、峰值天花板 −1.5 dBFS
（两者冲突时以峰值为准）、首尾 60 ms 淡化、统一裁 10 秒。
双格式 `m4a`(AAC 64k) + `mp3`，`preload="none"` 按需加载，总计 3.3 MB。

## 〇之三、配对图鉴与分享海报

### A. 配对图鉴（结果页）

结果页末尾有一组 4×4 的格子：**把朋友测到的乐器找出来，就知道你们俩凑在一起是什么关系。**
不需要账号、不需要后端 —— 纯静态就能成立。

**为什么恰好是 16 格、16 种关系，不重不漏：**

16 件主乐器各占四条轴的一个组合（`LOSB`…`CIWD`），把 16 格占满。
关系由两人代号的**逐位差异**决定，差异组合也正好 16 种。
拿「我的代号」对 16 件乐器逐一异或，结果必然互不相同 —— 所以
**16 件乐器 ↔ 16 种关系是一一对应的**，既不会重复也不会漏掉某一种。

格子按「相反的轴数」从少到多排序，所以从左上到右下就是从最像到最互补。
第一格必然是 `m0`「一个人的两把琴」，最后一格必然是 `m15`「正反两面」。

**「我的代号」从哪来（这一步决定了稀有款能不能有图鉴）：**

| 入口 | 代号来源 |
|---|---|
| 自己答完 24 题 | `resolve()` 带出的 `mycode`（由答案算出，**稀有款同样有**） |
| 别人分享的链接 / 从图鉴点进来 | 退而用该乐器自身的 `code` 字段 |
| 分享链接指向**稀有款** | 两者都没有 → **整段图鉴不渲染** |

最后一种是刻意的：稀有款不是四轴上的某一格，而是走到极端才会出现的结果，
没有确定的代号。这里不编一个假代号糊过去 —— 宁可不显示，也不给错的关系。
（已实测：`#r=ocarina` 进入时图鉴为 0 格，页面其余部分正常。）

自己那一格带描边标注，否则「一个人的两把琴」会让人以为算错了。

### B. 分享海报加「你最合拍的乐器」

海报底部、分隔线之上加了一行：标签 + 搭档缩略图 + 名称产地。
搭档是数据里一对一写死的（见 5.5），不是运行时算的，所以海报可以直接画。

画布随之从 1080×1960 加高到 **1080×2160**。注意这里**不能**让搭档区跟着正文往下排 ——
底部区块（分隔线、搭档区、二维码）全部**从下边缘反向定位**，并用两条断言守住：

```python
assert y <= div_y - 186          # 正文不能撞到搭档区
assert content_bottom <= div_y-12 # 搭档区不能压到分隔线
```

第一版就是被第二条断言拦下来的（差 4px）。这正是早先「判词两行把二维码挤到离底边
只剩 8px」那个 bug 的同类，所以这次直接写成断言而不是靠眼看。

二维码重新验过：21/21 可解码，缩到 378px 宽仍可扫。

## 一、灵魂主题

### 1.1 主命题

**「你不是没有表达欲，你只是还没找到自己的音色。」**

测试对外承诺的不是"测你像哪件乐器"（这是玩法），而是：

> **有一件乐器，在你还不会形容自己的时候，就已经在替你说话了。**

这句话是整个产品的灵魂锚点。它把一次娱乐测试升格为一个关于"自我表达困境"的命题 —— 几乎所有人都体验过"我心里有东西，但说出来就变形了"，这是普遍且私密的痛点，比"测你的性格"有效得多。

### 1.2 为什么用乐器而不用别的

乐器是极少数同时满足以下四点的载体：

| 特性 | 说明 |
|---|---|
| **音色即人格** | 音色是一种无法伪装的特质，天然对应"真实的自己" |
| **有实体美感** | 可以画成好看的水彩，具备视觉传播力 |
| **有知识增量** | 每件乐器背后有地理、工艺、声学，用户能真的学到东西 |
| **天然有关系性** | 乐器需要合奏，直接生成"找搭档"的社交钩子 |

### 1.3 文案调性三原则

1. **不奉承**。每个结果都有 `shadow`（阴影面）。只夸不痛的测试没有可信度，用户会觉得"这套话对谁都能说"。
2. **不玄学**。不写"你的灵魂频率是 432Hz"这类伪科学。所有 `learn` / `story` / `trivia` 的内容都必须是可核实的事实。
3. **第二人称、短句、有画面**。判词的目标是让人想截图，而不是让人读完点头。

### 1.4 为什么卡片上要有文化故事

纯乐器科普（几根弦、什么木头、什么原理）能建立可信度，但**不会被转发**。转发需要的是能让人产生情绪的东西，而情绪来自人的故事，不来自器物参数。

对比一下同一件乐器的两种写法：

| 写法 | 内容 | 效果 |
|---|---|---|
| 只有科普 | "钢鼓由钢制油桶端面锤打凹陷、划分音区调音而成" | 知道了，然后呢 |
| 加上故事 | "鼓被禁了，竹子也被禁了，于是他们从垃圾堆里翻出油桶，敲出了一件全新的乐器" | 想发给别人看 |

所以 21 件乐器全部配了 `story` 字段。挑选故事的四个标准：

1. **有人、有转折**——不是器物说明，是"发生了什么事"
2. **能对应人格**——故事的内核要与该乐器的人格判词呼应（钢鼓的"禁令中长出来"对应它的"选择明亮"；键控提琴的"一个人救回一件乐器"对应它的"自带回响"）
3. **可核实**——不用民间传说冒充史实。属于传说的明确写成传说（如康特勒琴的鱼骨故事写明出自史诗《卡莱瓦拉》）
4. **不猎奇、不消费苦难**——涉及殖民与奴隶制的故事（钢鼓、卡宏鼓）落点在**创造力与韧性**，而不是渲染压迫细节

几个特别有力的：钢鼓（禁令三次升级，最后从工业垃圾里诞生国家乐器）、卡宏鼓（能伪装成凳子躲过检查，1977 年被 Paco de Lucía 带进弗拉门戈）、键控提琴（1960 年代末只剩不到五个演奏者，一个人把它救回来，今天约一万人在拉）、手碟（必须手写信说明为什么想要，被选中才卖，2013 年停产）。

### 1.5 命名与文案素材

- 中文名：**声之肖像**
- 英文名：**Echoes of You**
- 主 slogan：找到那件替你说话的乐器
- 开场页文案：

  > 有些话你说不出来。
  > 不是因为不想说，是因为语言这件工具，
  > 不是为你这种人设计的。
  >
  > 世界上有 1500 多种乐器，
  > 每一种都在解决同一个问题：
  > 怎么把说不出口的东西发出声来。
  >
  > 12 个问题，找到你的那一件。

- 结束页分享引导：**「把你的音色发出来，看看谁能和你合奏。」**

## 二、页面流程

### 2.1 五个阶段

```
S0 开场页  →  S1 答题页 ×12  →  S2 计算过场  →  S3 结果卡  →  S4 分享/延伸
```

| 阶段 | 目标 | 关键设计 |
|---|---|---|
| **S0 开场** | 建立情绪、降低启动成本 | 只有一个按钮。明确写"12 题，约 90 秒"，消除时间焦虑 |
| **S1 答题** | 12 题，每题二选一 | 单题单屏，选完自动进下一题（不要"下一题"按钮）。顶部细进度条 |
| **S2 过场** | 制造揭晓期待 | 1.5–2 秒，四条轴依次落定的动画。**不要**假装在"分析数据"，直接呈现四轴结果 |
| **S3 结果卡** | 交付价值 | 一张竖长卡片：乐器水彩图 + **12 秒代表声音** + 判词 + 人格描写 + 阴影面 + **文化故事** + 构造科普 + 冷知识 + 搭档 |
| **S4 分享** | 传播 | 长按保存图片 / 复制链接 / 重测。附"查看全部 16 种音色"入口 |

### 2.2 答题页交互细则

- **每屏只一题**，题干 2 行内，两个选项为上下两张卡片。
- 选项**不带 A/B 标号**，避免"选项测试"感；用情境描述而非形容词。
- 点击后卡片有 200ms 的按下反馈，然后整屏向左滑出。
- 支持**返回上一题**（左上角小箭头），但不显示已选答案高亮 —— 避免用户回头"优化"答案。
- 进度条只显示比例，不显示"第 3/12 题"的数字 —— 数字会让人算还剩多久。

### 2.3 结果卡结构（从上到下）

```
┌─────────────────────────────┐
│  你的音色                     │  ← 小字标签
│  苍远的独白者                  │  ← title，大字
│  杜杜克管 Duduk · 亚美尼亚      │  ← 名称 + 产地
├─────────────────────────────┤
│                             │
│      [ 水彩乐器插画 ]          │  ← 唯一的图，占比最大
│                             │
├─────────────────────────────┤
│  [ ▶ 听听它的声音 ]  12 秒        │  ← ★ 音频按钮，紧贴水彩图下方
├─────────────────────────────┤
│ "你不需要提高音量，            │  ← verdict 判词
│  房间自会安静下来听你说话。"     │     卡片视觉主文案
├─────────────────────────────┤
│ 关于你          portrait      │
│ 你的存在感来自密度而非音量……     │
├─────────────────────────────┤
│ 你的另一面      shadow        │  ← 建立可信度的关键区
│ 你把情绪压得太稳……             │
├─────────────────────────────┤
│ ◆ 永远需要第二个人 story_title │  ← ★ 故事区，卡片第二视觉焦点
│ 亚美尼亚人说，杜杜克管是唯一能哭  │     story
│ 的乐器。它从不独奏——旁边永远有  │     ★ 最具转发价值的区块
│ 第二支 dam duduk，用循环呼吸吹  │
│ 出一条永不断绝的低音……          │
├─────────────────────────────┤
│ 关于它          learn         │  ← 构造科普，支撑可信度
│ 杏木制成，配一枚宽大的芦苇双簧片…… │
│ ◆ 冷知识        trivia        │  ← 一条独立硬事实
│ 它几乎从不独自出现……            │
├─────────────────────────────┤
│ 你的合奏搭档     partner      │  ← 社交钩子
│ 卡瓦尔笛 Kaval · 巴尔干        │
│ 「去找到你的搭档」              │
├─────────────────────────────┤
│  四轴条形图（你的坐标）          │
│  声之肖像 · 扫码测你的音色        │  ← 二维码
└─────────────────────────────┘
```

**设计要点：**

- **`story` 是卡片的第二视觉焦点**（第一是水彩图）。它讲人与命运，是最可能被单独截图转发的区块——给它独立的视觉容器、`story_title` 用略大字号并加符号前缀，不要埋进正文里。
- **内容顺序的逻辑**：先说你是谁（`portrait`）→ 再说你的暗面（`shadow`，建立可信度）→ 然后用故事把情绪推上去（`story`）→ 最后用硬知识收住（`learn` + `trivia`）。故事不能放在开头，那时用户只想知道"我是什么"，没耐心听别人的故事；而放在暗面之后，用户刚被说中，正是情绪打开的时刻。
- **三个知识字段严格分工，内容不得重叠**：

  | 字段 | 讲什么 | 承担的作用 |
  |---|---|---|
  | `story` | 讲**人与命运**——禁令、发明者、传说、时代 | 打动、被转发 |
  | `learn` | 讲**器物本身**——构造、材质、发声原理 | 可信度、真学到东西 |
  | `trivia` | 讲**一条独立硬事实** | 单独截图成立 |

  数据文件已做三字段交叉查重（`fix_trivia*.py`）。新增或修改文案后建议重跑查重，避免同一件事在一张卡上说三遍——那会让卡片显得很水。

### 2.4 乐器代表声音（音频）

音频紧贴水彩图下方，是「看见它」到「听见它」的自然衔接。**声音是这个产品最有说服力的一环** —— 判词说你"苍远"，用户听到杜杜克管的那一刻才真正明白这个词。

|---|---|
| **已有音频（15）** | 杜杜克管、键控提琴、古筝、葫芦丝、康特勒琴、手碟、桑图尔、马林巴、锡哨笛、卡林巴、恰朗戈、西库、玻璃竖琴、低音陶钵鼓、口簧琴 |
| **暂缺（1）** | 卡瓦尔笛 —— 唯一来源是仍在版权期的商业唱片数字化，不可用；结果页自动隐藏播放键 |

暂缺的 6 件在维基共享资源上确实没有合规可用的演奏音源（检索过英文、德文、西文、俄文、中文别名与分类树）。**注意其中钢鼓、卡宏鼓、马头琴、科拉琴、卡瓦尔笛都是主结果格**，即约三分之一的用户会落到无音频的乐器上，所以降级方案不是可选项，是必需项。

补齐途径（按推荐度）：
1. **委托录制** —— 找演奏者录 15 秒并签授权，音质与一致性最可控
2. **购买商用音源库** —— 世界乐器采样库通常含这几件
3. **Freesound.org** —— 需注册申请 API key，站内有大量 CC0 素材
4. 若最终补不齐，保持降级状态即可，不要用来源不明的音频上线

#### 关键技术约束

> **ogg 一律不能上线。** 维基共享资源的音频绝大多数是 `.ogg`，而 **iOS 在任何版本都不原生支持 ogg**。这个产品是移动端优先、要在微信里打开的，直接用 ogg 等于所有 iPhone 用户听不到声音。所有音频必须转成 `m4a`(AAC) 或 `mp3`。

`docs/_transcode.py` 已实现完整处理链，可复用：

| 步骤 | 做法 | 为什么 |
|---|---|---|
| 解码 | `soundfile` 读 ogg/wav/mp3 → 单声道 | 手机基本单扬声器，立体声无意义且体积翻倍 |
| 智能裁切 | 滑窗找 RMS 最高的 12 秒，并惩罚"开头即静音"的窗口 | 直接截前 12 秒常会截到空白或调音段 |
| 淡入淡出 | 首尾各 0.35 秒 | 不做会有明显爆音 |
| 峰值归一化 | 统一到 −1.5 dBFS | **必须做**：不同来源音量差极大，否则用户切换乐器时会被忽大忽小的音量吓到 |
| 输出 | m4a (AAC 96kbps) + mp3 | m4a 供 iOS/Safari，mp3 全平台兜底 |

单件约 145KB，15 件合计约 6MB。若嫌大可只保留 m4a（现代浏览器全支持 AAC），体积减半。

#### 播放交互（重要）

1. **绝不自动播放。** 移动端浏览器普遍拦截 autoplay，而且在地铁里突然出声会让用户直接关掉页面。必须由用户点击触发。
2. 按钮文案用 **「听听它的声音」**，标注时长（12 秒），让用户知道不会占用太久。
3. 播放时显示进度（简单的波形条或进度线即可），结束自动复位。
4. **同一时刻只播一个**：切换到搭档乐器的音频时，先停掉当前的。
5. `preload="none"` —— 不要预加载，否则 15 个音频会拖慢首屏。

```html
<audio id="snd" preload="none" playsinline>
  <source src="audio/duduk.m4a" type="audio/mp4">
  <source src="audio/duduk.mp3" type="audio/mpeg">
</audio>
```

```javascript
// 无音频时必须隐藏按钮，不能留一个点了没反应的按钮
const a = AUDIO.audio[id];
if (!a) { btn.hidden = true; }
else {
  btn.hidden = false;
  btn.onclick = () => {
    if (!snd.paused) { snd.pause(); snd.currentTime = 0; return; }
    snd.play().catch(() => { btn.hidden = true; });  // 播放失败就隐藏
  };
}
```

**降级原则：音频是加分项，不是依赖项。** 静音环境、加载失败、乐器无音源 —— 任何情况下卡片都必须依然完整可读。

#### 版权署名（必须做）

15 件音频里多数是 **CC BY** 或 **CC BY-SA**，这两种授权**强制要求署名**。做法：

- 音频按钮旁放一个小小的 **ⓘ** 或「音频来源」，点击展开：文件名、作者、许可证名称、原文件页链接
- 或在页面底部统一列出所有音频来源
- `docs/audio.json` 的每条 `credit` 字段已含 `file` / `author` / `license` / `license_url` / `page`，直接渲染即可

⚠️ **CC BY-SA 有传染性**：若你对音频做了实质性改编（本项目的裁切+归一化属于技术处理，一般不构成演绎，但保守起见仍应署名并标注原协议）。商用前建议逐条确认，或替换为 CC0/CC BY 音源。

试听验证页：`audio_preview.html`（本地起服务后打开，可逐条听、看时长与授权）。

- `trivia` 仍需单独成块带视觉强调，但**它不再是转发主力**，主力已交给 `story`。
- 四轴条形图放在最下方，作为"这不是随机结果"的信任凭证。

## 三、四条维度轴

采用荣格式二分法结构，但**不使用 MBTI 的四个字母**（E/I、S/N、T/F、J/P），避免被当成 MBTI 换皮，也避免版权与认知混淆。四条轴全部为原创的声音学隐喻。

| 轴 | 代号 | 正极 (+) | 负极 (−) | 心理学对应 |
|---|---|---|---|---|
| 1 | **R** 共鸣方式 | **L** 绵长余韵 | **C** 利落颗粒 | 信息处理的持续性：反复回味 vs 即刻处理完毕 |
| 2 | **E** 能量形态 | **O** 向外穿透 | **I** 向内低语 | 能量指向：外部影响 vs 内部深化 |
| 3 | **S** 结构关系 | **S** 独奏领航 | **W** 织体共生 | 关系定位：主导叙事 vs 互补协作 |
| 4 | **T** 情绪底色 | **B** 明亮欢腾 | **D** 深沉苍远 | 情绪基调：上扬 vs 内敛 |

**代号顺序固定为 R-E-S-T**（便于记忆，恰好拼成 "REST"）。
每个人得到一个四字母代号，如 `LOSD` = 绵长余韵 + 向外穿透 + 独奏领航 + 深沉苍远 = 杜杜克管。

### 3.1 为什么是 4 轴 16 格一对一

| 方案 | 问题 |
|---|---|
| 加权求和取最高分 | 会出现"永远测不到的乐器"，且无法解释为什么是这件 |
| 3 轴 8 格 | 只能容纳 8 件乐器，不够 |
| 5 轴 32 格 | 需要写 32 套文案，且题量必须上升到 15+ 题，完成率下降 |
| **4 轴 16 格一对一** ✅ | 每格必然可达、结果可解释、题量可控在 12 题 |

一对一映射还带来一个额外好处：**互补搭档可以严格定义**为"某几轴相反"的那一格，而不是随手指定。

### 4.1 出题原则（五档量表专属，务必遵守）

改用五档量表后，出题规则和二选一**完全不同**。踩过的坑：一开始只把选项换成五档、题干仍保留"A 而不是 B"的对比结构，结果非常别扭 —— 用户面对"我更喜欢 A 而不是 B"这种题，五个档位变成了"我有多同意选 A"，语义混乱，答案也失真。

**铁律：**

1. **每题只陈述一件事。** 绝不出现"而不是""比起""更可能""另一种"这类对比词，也不能有"比 X 更 Y"的结构。数据构建脚本 `build_data.py` 内置了检查器，命中即报错退出。
2. **描述具体可回忆的行为或反应**，不做抽象自评。写"一场聊得很好的对话结束后，那几句话还会在我脑子里响一路"，而不是"我是个爱回味的人"。后者答的是自我形象，不是真实反应。
3. **每轴必须有反向计分题**（`dir=-1`）。否则用户一路点"很像我"就能刷出满分极端结果。当前配置：R/E/S 轴各 2 正 1 反，T 轴 1 正 2 反。实测全选"很像我"只得 `R2 E2 S2 T-2`，不会失控。
4. **补充说明（hint）只做情境铺垫，不做对比。** 允许"比如某种黄昏"这类举例，禁止"而不是热闹的东西"。
5. **必须说人话。** 用日常口语，不要文学化表达，也不要指代不明。踩过的坑（已废弃的写法）：

   | ✗ 废弃写法 | 问题 | ✓ 改后 |
   |---|---|---|
   | 一些说不清的怅然的东西，很容易就把我留住了 | 这是散文不是问卷 | 我喜欢安静、慢节奏的东西 |
   | 站在很多人面前说话，紧张，但我确实想要那个位置 | "那个位置"指代不明 | 要在很多人面前讲话，我会紧张，但我愿意上 |
   | 我很在意每个人是不是都真的接上了 | "接上"太含糊 | 团队做事的时候，我会特别留意有没有人被落下 |

   `build_data.py` 内置**两个**检查器：对比词检查（铁律 1）+ 文学化/指代不明检查（本条）。命中即报错退出。

6. 题干控制在 32 字内（当前 13~25 字），保证手机单屏不挤。

7. **场景必须均衡，不能全是工作/自我视角。** 用户反馈过两次：先是"很多让人联想到工作和自我，但没有关于对周围人的感情的，亲情友情爱情这些"，随后又提"生活和独处/工作也可以稍微加一点，比如可以再加一些艺术/生活品味的个人题"。
   题目分四类场景标签，**`bond` 占比须 ≥1/3，`taste` 每轴至少一道**：

   | 场景 | 含义 | 当前 |
   |---|---|---|
   | `work` | 工作与做事 | 6 题 25% |
   | `self` | 独处与自我 | 4 题 17% |
   | `taste` | 生活与审美品味：听什么、穿什么、怎么安排自己的空间和时间 | 4 题 17% |
   | `bond` | 亲情 / 友情 / 爱情 | **10 题 42%** |

   `build_data.py` 会断言校验占比、`taste` 数量、以及四轴对 `bond`/`taste` 的覆盖。

   理由：人在亲密关系里的反应，比在工作里的表现更能定义"音色"；而审美偏好是"音色"最直接的外显 —— 一个人听什么、穿什么、怎么布置自己的空间，比他在工作里怎么做事更贴近"他本来是什么声音"。

8. **场景要交错，order 不要手填。** 手工排序踩过坑：把品味题统一放在 17~20、情感题放在 21~24，结果排出"连续 4 道品味 + 连续 4 道情感"的成块序列，用户答到后面会疲劳。
   现由 `build_data.py` 的 `arrange()` 自动生成 order：

   - 轴按 `R→E→S→T` 严格轮转，保证相邻题必不同轴（避免用户察觉规律）
   - 每步在当前轴的剩余题里，优先挑"场景与上一道不同"的那道

   题目元组里的第一个数字只表示**轴内次序**，最终编号由算法给出。检查器断言**最长同场景连续 ≤2 道**（当前实测 2 道）。

| 档位 | 文案 | 计分 |
|---|---|---|
| +2 | 很像我 | 圆点最大、金色实心 |
| +1 | 有点像 | 金色描边 |
| 0 | 说不好 | 虚线描边 |
| −1 | 不太像 | 紫色描边 |

## 五、计分算法（五档量表版）

> 权重与阈值经**按轴卷积**测算（5^12 = 2.44 亿种作答，逐个穷举不现实，
> 改为每轴独立枚举 125 种再做四轴组合）。验证脚本：`docs/verify_h5.js`

### 5.1 单题计分

```
题目得分 = 档位值(+2/+1/0/-1/-2) × 题目方向(dir) × 权重(w)
```

`dir` 用于反向计分题。每轴 6 题、权重 `[1,1,1,1,2,2]`，故单轴区间 **−16 ~ +16**。

### 5.2 0 分的处理（关键）

五档量表必然产生 0 分：**单轴得 0 的概率约 7.8%，四轴中至少一轴为 0 的概率仍有 27.8%**。

如果简单地把 0 归入某一极，那一轴就变成了掷硬币 —— 三分之一的用户会有一个维度是随机的。所以改用**分级打破平局**：

```javascript
function sign(ans, axis){
  // 1. 总分不为 0 -> 直接取符号
  // 2. 总分为 0 -> 看两道加权题(w=2)的合计方向
  // 3. 仍为 0 -> 看权重 1 那道题
  // 4. 全为 0（用户全选"说不好"）-> 归正极
}
```

这样即使总分为 0，也是由用户在**区分度最高的那两道题**上的倾向决定，而不是随机。

### 5.3 稀有款触发

强偏好阈值 **±6**（单轴满分 ±16），均衡型判定 **|v| ≤ 3** 且正负各占两轴。

| 稀有款 | 条件 | 实测触发率 |
|---|---|---|
| 西库 Siku | `S ≤ −6` 且 ≥3 轴达强偏好 | 1.43% |
| 口簧琴 Jaw harp | `R ≤ −6` 且 `S ≥ 6` | 1.25% |
| 陶笛 Ocarina | 四轴 `|v| ≤ 3` 且正负各 2 | 2.40% |
| 玻璃竖琴 Glass harp | `R ≥ 6` 且 `E ≤ −6` | 1.11% |
| 低音陶钵鼓 Udu | `E ≤ −6` 且 `T ≤ −6` | 0.97% |

### 5.4 实测分布

按轴卷积统计（5^24 ≈ 5.96×10^16 种作答组合，穷举不可能）：

| 指标 | 数值 |
|---|---|
| 主结果占比 | **90.2%** |
| 稀有款合计 | 9.80%（单款 1.36% ~ 2.53%） |
| 16 格覆盖 | **16/16，无死格** |
| 单格占比 | 4.97% ~ 6.88%（差 1.4x） |
| 需打破平局 | 每轴 7.8% |

稀有款实测触发率：西库 2.53%、陶笛 2.40%、口簧琴 1.88%、玻璃竖琴 1.62%、低音陶钵鼓 1.36%。

> **题量变化后必须重算阈值。** 每轴题数增加会让"全题同向"变难，稀有款随之更难触发：
> 24 题版按旧阈值 ±9 测，最冷稀有款只剩 **0.08%**（等于测不到）。
> 逐一枚举 `强阈值 × 均衡阈值` 后，**±6 / |v|≤3 是唯一同时满足"16 格全覆盖 + 最冷稀有款 ≥1% + 稀有合计 4~12%"的组合**。

极端作答检查：

| 作答 | 四轴分数 | 结果 |
|---|---|---|
| 全选「很像我」 | R0 E0 S0 T0 | 键控提琴 + 低区分度提示 |
| 全选「完全不像」 | R0 E0 S0 T0 | 同上 |
| 全选「说不好」 | R0 E0 S0 T0 | 同上 |

24 题版各轴的**加权方向和恰好为 0**（3 正 3 反且权重对称），所以全选同一档位时四轴必然全为 0 —— 这是最强的防刷形态，任何"一路点同意"都无法制造偏向。

**两层防护：**

1. **乱答防护** `isLazy()`：全选同一档位时跳过稀有款判定。否则四轴全 0 会掉进"均衡型"稀有款 —— 而"均衡"应该是真实的无偏好，不是无效作答。
2. **低区分度提示** `weak`：四轴全为 0（含全选同档位、以及正反抵消的巧合作答）时，结果卡顶部显示一行说明 ——「你的每个维度都几乎持平，这一件是最接近的那个。想更准的话，可以重测一次，遇到犹豫的题就凭第一反应选。」
   静默返回一个任意结果不够诚实，明说反而更可信。正常作答不会触发（已实测验证）。

复跑验证：
```bash
node docs/verify_h5.js
```

### 5.5 互补搭档逻辑

`partner` 字段在数据中一对一写死，并非算法实时计算。设计规则是取 S 轴、T 轴相反的那一格附近的乐器，再人工校准文化搭配的合理性 —— 例如杜杜克管 ↔ 卡瓦尔笛，同为气鸣乐器、地理相邻，现实中合奏成立。

写死而非计算的理由：算法生成的搭档常出现文化上很怪的组合，而 21 组人工校准的成本很低。

## 六、分享机制

### 6.1 结果卡生成为图片

移动端浏览器无法可靠地直接"保存 DOM"，方案：

- 用 **html2canvas**（CDN: cdnjs / jsdelivr / unpkg）把结果卡节点渲染为 canvas，再转 dataURL 显示为 `<img>`，提示用户**长按保存**。
- 关键坑：
  - 必须等乐器图 `onload` 完成再截图，否则图是空的
  - 设 `scale: 2` 保证高清，但要注意超长卡片在低端机上的内存
  - 乐器图若来自外部域名，需 `useCORS: true` 且图源支持 CORS；**建议直接把 21 张图打包进项目本地目录**，彻底规避

### 6.2 链接分享携带结果

用 URL hash 携带代号，让被分享者能直接看到你的结果卡：

```
index.html#r=LOSD          // 主结果
index.html#r=siku          // 稀有款
```

打开带 hash 的链接时，直接渲染 S3 结果卡，并在底部加一个显眼的
**「测测我自己的」** 按钮 —— 这是二次传播的关键转化点。

### 6.3 "查看全部音色"图鉴页

结果页底部提供入口，展示 16 件主乐器的水彩缩略图网格（稀有款显示为剪影 + 「?」，未解锁）。

这个页面的作用是**制造重测动机**："我想要那个稀有的"。

## 七、技术实现要点

### 7.1 技术选型

**单个 HTML 文件 + 本地图片目录**，不用任何框架。

理由：这是一个纯静态、无状态、需要在微信内打开的分享型页面。任何构建工具都是纯负担。

```
echoes-of-you/
├── index.html            # 全部结构 + 样式 + 逻辑
├── audio_preview.html    # 音频试听验证页（开发用，不上线）
├── docs/
│   ├── instruments.json      # 21 件乐器全部文案数据
│   ├── audio.json            # 音频清单 + 版权署名信息
│   ├── framework.md
│   ├── compliance-and-art.md
│   ├── verify_scoring.py     # 计分穷举验证
│   └── _transcode.py         # 音频裁切转码（补新音频时复用）
├── img/
│   ├── duduk.png         # 21 张水彩图（待生成）
│   └── ...
├── audio/                # 上线用：15 × (m4a + mp3)，约 6MB
│   ├── duduk.m4a
│   ├── duduk.mp3
│   └── ...
└── audio_src/            # 原始下载文件，保留以便重新裁切（不上线，约 53MB）
```

数据可以直接内联进 `index.html` 的 `<script>`，避免 `file://` 协议下 `fetch` 本地 JSON 被 CORS 拦截 —— **这是最容易踩的坑**，用户直接双击打开 HTML 时 `fetch('./docs/instruments.json')` 会失败。

### 7.2 移动端适配

| 项 | 做法 |
|---|---|
| 视口 | `<meta name="viewport" content="width=device-width,initial-scale=1,viewport-fit=cover">` |
| 高度单位 | 用 `100dvh` 而非 `100vh`，避免移动端地址栏导致的跳动；加 `100vh` 作降级 |
| 安全区 | `padding-bottom: env(safe-area-inset-bottom)` |
| 字号 | 正文 ≥ 15px；判词 20–24px |
| 点击区 | 选项卡片最小高度 ≥ 64px |
| 禁用缩放 | 不要禁用（无障碍问题），改为把布局做稳 |
| 字体 | 用系统字体栈，不加载网络字体（微信内加载慢）。中文衬线可用 `Songti SC / STSong / serif` 作为判词字体 |

### 7.3 状态管理

```javascript
const state = {
  step: 0,              // 0=开场 1..12=答题 13=过场 14=结果
  answers: [],          // [{ axis:'R', delta:1 }, ...]
  scores: { R:0, E:0, S:0, T:0 }
};
```

答案存在内存即可，**不需要 localStorage** —— 这个测试的价值在于一次性的揭晓，"恢复上次进度"是伪需求。

### 7.4 动画

- 题目切换：`transform: translateX()` + `opacity`，200–250ms
- 过场四轴落定：每条轴延迟 200ms 依次动画，总时长 1.5s 左右
- 结果卡：从下往上 `translateY` 淡入
- 全部动画包在 `@media (prefers-reduced-motion: no-preference)` 里
- **只用 `transform` 和 `opacity`**，其他属性会触发重排，低端机上会卡

### 7.5 建议的实现顺序

1. 数据内联 + 计分函数（先用 console 验证 16 格都能测到）
2. 结果卡静态样式（先写死一个乐器，把最难的视觉调好）
3. 答题流程 + 动画
4. 开场页 + 过场页
5. html2canvas 保存 + hash 分享
6. 图鉴页

**先做结果卡**是关键 —— 它是整个产品的价值交付点，也是样式最复杂的部分。先把它做对，前面的流程都是简单页面。
